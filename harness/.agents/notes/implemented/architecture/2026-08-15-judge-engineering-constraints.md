# Agent Note: 思考型裁判的工程约束（E2/E9 实证）

Status: implemented

## Problem

评测是 harness 的护城河，但思考型裁判（Qwen3.5-27B 开启 thinking）会先在
思考文本里烧光 token 预算，导致评分 JSON 根本没输出——实测触发段 3/4 被误判 5.0。
裁判质量本身很高（对段 1 的描述与评分和人工判断一致：9.17/9.67），
问题全部在工程侧而非模型能力。

## Decision

裁判适配器（`judge.openai-compat`）固化三条工程约束：

1. **enable_thinking=false**（`disable_thinking: true` 默认值，经 vLLM
   `chat_template_kwargs` 透传）——防思考文本燃烧 token 预算；
2. **max_tokens=4096**——评分 JSON 的硬预算；
3. **维度别名正则兜底**——思考模型常省略维度前缀（"与指令一致性"→"一致性"），
   解析器按 `aliases` 匹配；JSON 解析失败时按正则兜底。

可靠性审计（E9，33 次真实调用）：JSON 直接解析 29/33（88%），正则兜底 4/33（12%），
完全失败 0。分数分布 min=0 max=10 mean=7.52，重试阈值 6 具有区分度。

配套纪律（评分纪律写进裁判 prompt）：10 分只给无可挑剔的完美输出；存在任何明显缺陷
最多 6 分；平均分不应超过 8 分——防止裁判分数通胀失去区分度。

## Alternatives considered

- **让裁判保持 thinking 开启换更深思考**：否决。预算约束是硬约束；评测是
  批量调用的成本大户，确定性（同输入同输出）比分深思考更重要。
- **解析失败静默给低分重试**：否决。解析失败必须可观测（缺失维度计 0 并判未通过，
  见 judge 结算归属笔记），而不是藏在重试里掩盖系统性解析问题。
- **用专用小模型评分（非 VLM）**：否决。评测对象是多模态（视频帧+音频标签），
  文本-only 模型无法覆盖画面维度。

## Consequences

- 裁判解析 100% 可用（E9 基线）；任何新裁判提供者必须满足同一工程约束
  （协议笔记的 spec_to_criteria 兼容层保证别名机制统一生效）。
- 需要更严谨评分的实验可通过 `disable_thinking: false` 显式覆盖，
  同时承担 token 燃烧风险——这是显式的任务级选择，不是隐藏默认。
